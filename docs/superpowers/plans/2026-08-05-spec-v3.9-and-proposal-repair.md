- [ ] **Step 2: Fix P9 — it cannot execute as written**

In §3.10, `trent` owns nothing, so `GET /api/v1/accounts` returns an empty list for him. §11 has the
CLI resolve `--account ACC-001` to a uid **through that list**, and §9.6 runs the scenario catalogue
through the CLI's client. So P9 cannot resolve `ACC-001`.

Neither obvious fix works. Giving `trent` an account lets him resolve *his own*, not `alice`'s.
Widening `GET /accounts` for admin is forbidden — see Step 4.

Mark **[repaired]** and state: **P9 references the deterministic `accountUid` directly, not the
account name.** §6.4 already pins `ACC-001`…`ACC-900` to deterministic UUIDs via the realm file and
seed script "so scenarios can reference them". No realm change, no CLI change, and N12 continues to
hold for `trent`.

- [ ] **Step 3: State how `actor` reaches the audit trail**

The largest hole. Read `src/main/java/com/ffroliva/tinyledger/audit/adapter/in/events/AuditKafkaListener.java`
first — it states the audit module never parses the ledger event's JSON; every stored field comes
from Kafka headers. So `actor` arrives either via a **header**, which is transport-level and may
silently disagree with the immutable payload, or by parsing the payload, which breaks the module's
stated independence. The proposal says nothing.

Mark **[repaired]** in §2 (D3/D4) and add, before choosing a transport:

```markdown
**The event payload is the record; the audit trail is a projection of it.** Whichever transport
carries `actor` to the `audit` module, a trail entry whose `actor` disagrees with the payload is a
fault, and E8's rebuild must surface it. That constraint holds either way and is what makes the
transport choice safe to defer to the implementing plan.
```

- [ ] **Step 4: Forbid widening the account collection**

Add to §2, marked **[repaired]**:

```markdown
**D8 — `ledger:admin` never widens `GET /api/v1/accounts`.** N12 holds for `trent`. The collection
endpoint encodes authorisation in the port signature (`accountsOwnedBy(String owner)`), so widening
it is a port-signature change, not a clause — and a widened collection enumerates every customer's
account, voiding §6.5's "`accountUid`s are unguessable" premise, which is the stated justification
for answering wrong-owner access with 403 rather than 404.
```

- [ ] **Step 5: Replace absence-means-owner with a cutover instant**

§15.9 / D7 say an absent `actor` reads as `actor = owner`, "an exact inference, not a default". It is
not exact: `actor` lives in payload JSONB with no DDL, no `NOT NULL` and no schema marker, so a
post-change event whose stamping was dropped is byte-identical to a legacy one — and the spec would
instruct attributing it to the owner.

Mark **[repaired]** and replace with: absence reads as `actor = owner` **only for events whose
`occurredAt` precedes the cutover instant recorded when this lands**. After it, absence is a defect
and the trail reports `unknown`, never the owner.

- [ ] **Step 6: State that replays record no actor**

`RecordMovementService` returns the replay before emitting any event, and `samePayload` compares
accountId, type, amount and reference — **not the caller**. So a replayed movement emits nothing and
records no actor.

Mark **[repaired]** in §2 and add: *the log records who **first** performed a movement, not everyone
who subsequently requested it.* Without this, §3.2's claim that "who acted survives in the log" is
false for replays.

- [ ] **Step 7: Fix the two edits that assume a single decorator**

Both contradict Task 1's §6.4.

- **§3.5** preserves "inside that wrapper". Mark **[superseded]** and point at v3.9's §6.4 — the
  admin clause applies at every site in that section's table, not in one wrapper.
- **§3.7** is worse: it rewrites the document's *correct* phrase "the use case compares the two" into
  "**the decorator** compares the two". Mark **[repaired]** and keep the original phrase, adding only
  the admin clause: *"the use case compares the two, and where they differ admits the caller only if
  they hold `ledger:admin`"*.

- [ ] **Step 8: Correct the impact inventory**

§4 claims *"One clause in one predicate — the shared ownership comparison both the command and query
decorators route through."* There is no shared predicate and no command decorator. Mark **[repaired]**:
the clause lands at **three** comparison sites (`AuthorizedUseCases.requireOwner`,
`RecordMovementService`, `StrongBalanceService`), and the collection endpoint is excluded by D8. Note
that `requireOwner` is `private static` in `config` and the cycle rule forbids `ledger.application`
importing `config`, so a genuinely shared predicate would have to be a new type in `shared`.

- [ ] **Step 9: Split N13 and add the missing negatives**

§3.10's N13 covers one auditor route. `SecurityConfig` denies `/api/v1/audit/**` **and**
`/api/v1/accounts/*/events` together, and `getEvents` returns event payloads verbatim — the richer
surface. A matcher covering only `/audit/**` would pass N13 while an admin reads the other.

Mark **[repaired]**: split N13 into one scenario per auditor route, and add these negatives, each
with its reason:

| Scenario | Asserts |
|---|---|
| `trent` **without** `ledger:writer` attempts a cross-account deposit | 403. The actual conjunction test — P9 cannot fail against a short-circuit that also grants roles |
| `trent` requests `GET /api/v1/accounts` | Only accounts he owns. Proves D8 |
| `mallory` (writer, no admin) attempts a cross-account write | 403. Proves the widening is gated on the role rather than always-on |
| An event written after the cutover with no `actor` | Reported as `unknown`, never as the owner |

Also flag: §5's hardcoded scenario ID set `(P0…P8, N1…N12, E1…E9)` goes stale the moment P9 and N13
exist, and the proposal's exact-edit list omits it. Add it to the edit list.

- [ ] **Step 10: Soften the separation-of-duties claim**

D2 says an admin "must not also be the principal who reviews the record of those movements". That
over-claims: widening `ledger:reader` gives an admin every account's transactions and balances, which
*is* the record. Mark **[repaired]**: what separation of duties withholds is **attribution**, not the
record.

Add an **OPEN QUESTION** block, unresolved, for the plan that implements admin:

```markdown
**OPEN — requires a product decision before implementation.** Should `ledger:admin` widen the
ownership term for *reads* at all, or only for change operations? Widening reads lets an operator
browse every customer's balances and transactions; the stated motivation (fraud response, court
order) is about *acting*. Narrowing admin to change operations only is a tighter posture and departs
from D1's uniform widening. Not decided.
```
