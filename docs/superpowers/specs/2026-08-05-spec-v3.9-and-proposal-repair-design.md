# Design — spec v3.9, and repairing the admin on-behalf-of proposal

**Status:** approved by the product owner 2026-08-05, after a four-lens council.
**Scope:** documentation only. No production code changes.
**Follows:** Plan 3 (security and authorization), merged at `88631f9`.
**Precedes:** the roles + Keycloak realm plan, then the admin on-behalf-of plan.

---

## 1. Why this exists

`docs/spec.md` §6.4 says authorisation is applied by **one** decorator at the port boundary. After
Plan 3 the code enforces it in **four** places. The document is wrong, and nothing in the build fails
because of it — a spec has no test gate. That is how the divergence arose and why it cannot be left.

A second problem sits behind it. The approved `admin-on-behalf-of` proposal contains thirteen
pre-written spec edits, and **two of them assume the single decorator** — §3.5 preserves "inside that
wrapper", and §3.7 actively rewrites "the use case compares the two" into "**the decorator** compares
the two". Applying the proposal as approved would have re-broken §6.4 in a second place while the first
was being fixed.

## 2. What the council found

Four advisors reviewed the first draft of the §6.4 amendment. **All four rejected it.** The findings
that shaped this design:

| Finding | Lens |
|---|---|
| Three of the four justifications for the hybrid do not survive the code. "A boundary check cannot tell absent from unowned" is **false** — `AuthorizedUseCases:62-66` already does exactly that. The `@Primary` collision is an implementation constraint, and `UseCaseConfig:26-27` documents the escape hatch. §6.3's ordering supports neither option. | code-architect |
| Only one reason is durable, and it is stronger restated: the check must be taken against **the same state, at the same version, the command is applied to**. That survives a strongly-consistent projection; "a decorator runs before the stream is read" does not. | code-architect, staff-reviewer |
| The draft's §9.2 claim is **factually wrong and already shipped**: `@PreAuthorize` is not a Spring stereotype, and the enforced rule bans exactly `@Service`, `@Component`, `@Transactional`. Duplicated at §4.5. | spec-editor |
| "Two places" is wrong in both directions — four sites, and the controller's `accountsOwnedBy` filter answers **404 for wrong-owner**, contradicting the very section being amended. | code-architect, staff-reviewer, security-auditor |
| The text asserts "the operation's role check **and** …" when **no role check exists anywhere**. Today §6.4 is wrong about *where*; the draft would make it wrong about *whether*. | all four |
| "Enforced in two places" reads as a licence for a fifth. Needs a principle, an enumeration, and a closure clause. | staff-reviewer |
| Terminology: "port boundary" and "projection-backed" appear **zero** times in the spec; the settled terms are "inbound port" and "read models". "The event stream is the system of record" drifts from §4.2, which says the event **store** is. | spec-editor |

## 3. The v3.9 §6.4 mechanism paragraph

Replaces the current two-sentence mechanism paragraph. Principle first, sites derived from it,
list closed.

> Authorisation is a use-case concern, never a controller concern, applied in the composition root
> (§4.5) rather than by annotation — the application layer carries no Spring annotations (§4.5).
>
> **Every authorisation decision is made by the component that holds the state the decision needs.**
> That principle decides where a new operation's check belongs. It yields four sites, and **this list
> is closed — a fifth requires an ADR.**
>
> | The operation | Authorised | Because |
> |---|---|---|
> | Changes state, or reads at the aggregate's version (`?consistency=strong`) | In the service, against the rehydrated aggregate, before the idempotency lookup (§6.3) | The decision must be taken against the same state, at the same version, the command is applied to |
> | Reads a read model for one named account | A decorator wrapping the inbound port (§4.5) | The read model is the authority for a question the read model answers |
> | Returns a collection the caller sees only part of | The port takes the visibility scope as a parameter (`accountsOwnedBy`) — the scope *is* the authorisation | There is no set to decorate; widening it is a port-signature change |
> | Depends on role alone, with no account subject (`/audit/**`, `/accounts/*/events`) | The security filter chain in `config` | There is no subject to compare and no inbound port to decorate |
>
> Absent is never answered as unowned: an account that does not exist is §6.5's 404, whoever asks.

**Deliberately absent:** any sentence about role checks or `ledger:admin`. Neither exists in the code,
and §3 of this design explains why they land with their implementation instead.

## 4. What else v3.9 contains

1. **Fix the §9.2 error in both places** — §6.4's mechanism paragraph and §4.5's "§9.2 forbids them
   there". Cite §4.5's design rule, which does forbid framework annotations in the application layer,
   rather than §9.2's enforced rule, which bans three specific annotations and not `@PreAuthorize`.
2. **Record the two known divergences** where a reader will find them, not only in Javadoc:
   `GET /accounts/{accountUid}` answers **404** for a wrong-owner account where §6.5 requires 403, and
   `GET /accounts/{id}/transactions` answers **200 with an empty page** for an unknown account where
   §6.5 requires 404.
3. **Name the temporary denial.** `full` refuses both auditor routes with 403 pending `ledger:auditor`,
   with its exit condition stated.
4. **`POST /api/v1/accounts` is authorised by nothing today**, though §7 annotates it `ledger:writer`.
   Record it as a gap rather than leave §7 implying enforcement.
5. **Add §7.2, the Open Banking alignment table** — with a build-status column. The table's verdicts
   include "Adopt" for DPoP, which is not built; without status the table asserts conformance the code
   does not have, which is the same disease as §6.4.
6. **One revision-history row** for v3.9. The document's convention is one row per version.

## 5. Repairing the admin on-behalf-of proposal

Not applied to the spec in this pass. Repaired so the plan that implements it can be written from it.
Four defects, all found by the council:

| # | Defect | Repair |
|---|---|---|
| 1 | **P9 is unrunnable.** `trent` owns nothing, so his account list is empty — and §11 resolves `--account ACC-001` through that list while §9.6 runs the catalogue through the CLI. | Give `trent` an owned account, or specify uid resolution that does not depend on the caller's own list. |
| 2 | **`actor` has no stated route into the audit trail.** `AuditKafkaListener` never parses the event JSON; every field comes from Kafka headers. So `actor` arrives via a **forgeable header** that may silently disagree with the immutable payload, or by breaking the module's independence. The proposal is silent. | Pick a transport — but under a constraint the repair must state first: **the event payload is the record, and the trail is a projection of it.** A trail entry whose `actor` disagrees with the payload is a fault E8's rebuild must surface. That constraint holds whichever transport wins, and without it the choice is unconstrained. |
| 3 | **"Absence of `actor` means the owner acted" is unfalsifiable.** No DDL, no `NOT NULL`, no cutover marker — a post-change event with dropped stamping is byte-identical to a legacy one, and the spec would instruct attributing it to the owner. | A cutover instant: absence before it reads as the owner; absence after it is a defect and reports `unknown`. |
| 4 | **Replays record no actor.** `samePayload` does not compare the caller and a replay emits no event, so an admin can drive a `200` on the money path with no trace. | State that the log records who *first* performed a movement, not everyone who requested it. |

Also correct in the same pass, all council findings against the proposal's own text:

- **§3.5 and §3.7 both assume the single decorator.** §3.7 is worse — it *introduces* the error.
- **The impact inventory is wrong.** "One clause in one predicate" — there is no shared predicate; the
  clause lands at three sites, and `accountsOwnedBy` is a **port-signature change**, not a clause.
- **`ledger:admin` must not widen `GET /api/v1/accounts`.** A widened collection enumerates every
  customer and voids §6.5's unguessable-UUID premise. N12 must hold for `trent`.
- **N13 covers one of two auditor routes.** `getEvents` returns event payloads verbatim; a matcher
  covering only `/audit/**` passes N13 while an admin reads the richer surface. Split into two.
- **The separation-of-duties rationale over-claims.** Widening `ledger:reader` gives an admin every
  account's transactions and balances — that *is* the record. What separation withholds is
  **attribution**, not the record. Say so.
- **§5's hardcoded scenario ID set** `(P0…P8, N1…N12, E1…E9)` goes stale when P9/N13 are added, and the
  proposal's edit list omits it.
- Add the missing negative scenarios: `trent` **without** `ledger:writer` refused; `trent` on
  `/events` refused; `trent`'s own account list not widened; `mallory` cross-account write refused.

## 6. Sequencing, and why the spec text is split

Council recommendation, accepted: **v3.9 contains only what is true at HEAD.** Roles, `ledger:admin`
and `actor` land in the spec **in the same commit as the code that implements them**.

The reason is the one this whole design turns on: a spec has no test gate, so prose that describes
unbuilt behaviour has nothing to hold it accountable and no way for a reader to distinguish it from
prose that describes shipped behaviour. Landing spec text with its implementation makes the code the
gate the document otherwise lacks. §6.4 drifted precisely because that was not done.

## 7. Testing and gates — stated honestly

There is **no automated gate on spec correctness**. `check_docs_governance.py` verifies the document
inventory, not the truth of any sentence. `spotless` does not touch Markdown. Nothing in `verify` or
`-Pit` fails if §6.4 lies.

**The council review is the gate.** That is the whole of it, and the plan should say so rather than
implying CI covers it. The one mechanical check available is that every `§` cross-reference in changed
text resolves and says what is claimed — the audit that found the §9.2 error.

## 8. Explicitly out of scope

- Any production code change. The two divergences listed in §4 item 2 above are **recorded, not fixed** —
  each needs its own test and its own decision.
- Applying admin on-behalf-of to the spec.
- Role checks, the Keycloak realm, DPoP.
- Fixing the `POST /accounts` authorisation gap. Recorded in v3.9; closed by the roles plan.
